# 마이그레이션·장애 복구

## 마이그레이션 전

- DB 스냅샷/PITR 시점을 기록하고 백업을 별도 프로젝트에 복원해 확인합니다.
- Cron과 새로운 결제 Checkout을 일시 중지하고 진행 중인 발행·결제 작업을 점검합니다.
- TOKEN_ENCRYPTION_KEY를 비밀 저장소에 백업합니다. DB만 복원하고 키를 잃으면 연결 토큰을 복호화할 수 없습니다.
- PHASE 2에서 PHASE 3는 `002_phase3_operations.sql` 한 트랜잭션으로 실행합니다. 오류 시 PostgreSQL transaction이 rollback되며 부분 적용 상태로 진행하지 않습니다.

## 롤백 전략

PHASE 3의 구독·게시·사용량을 삭제하는 DROP 기반 롤백은 제공하지 않습니다. 데이터 손상을 피하려면 우선 서비스를 유지보수 모드로 전환하고 Cron·Checkout을 중지한 뒤 **전진 수정**을 적용합니다. 스키마만 PHASE 2로 덮어쓰면 플랜/보안 검사가 제거되므로 금지합니다.

복구가 필요하면 기록한 PITR 시점의 백업을 **새 Supabase 프로젝트**에 복원하고, 새 환경에서 RLS·데이터·카운터·구독·암호화 키를 검증한 뒤 APP의 DB 연결을 전환합니다. 원본 DB는 보존합니다. 외부 Stripe/Meta에서 이미 발생한 결제·게시를 DB 복원으로 취소할 수 없습니다.

- Stripe 현재 구독·청구를 조회하고 서명된 이벤트 재전송/사용자 소유 구독 동기화로 권한을 대조합니다.
- 과거 시점 복원으로 AI 카운터가 감소했으면 제공자/감사 기록과 대조해 카운터를 **증가시키는 방향으로** 복구합니다.
- Threads 게시 결과가 불명확하면 provider post ID·실계정을 확인합니다. 확인 전에는 uncertain을 지우거나 job을 재등록하지 마세요.
- OAuth/결제 키 노출 시 키를 회전하고 재배포합니다. 암호화 키 교체는 기존 토큰 재암호화 또는 사용자 재연결과 함께 수행합니다. 새 키만 덮어써 기존 암호문을 잃지 마세요.

## 예약 작업 장애

`publishing` lease가 5분을 넘으면 다음 worker가 `failed + uncertain`으로 분리하며 자동 재시도하지 않습니다. 원격 게시 성공 여부를 확인하지 않고 다시 게시하면 중복될 수 있습니다. 확실히 게시되지 않은 일시 실패만 최대 3회 재시도합니다. 대기/처리 중 콘텐츠 삭제는 DB trigger로 차단됩니다.

## 보존·백업 운영

Supabase 백업/PITR, 결제 제공자 원장, 토큰 키 백업을 별도로 유지합니다. audit_logs·api_errors·rate_limits·active_users의 보존 기간과 정리 작업은 운영 정책에 맞춰 추가해야 합니다. 현재 코드는 자동 삭제나 사용자 데이터 초기화를 수행하지 않습니다.
